## Project rules
- Store categories live in the `categories` table (id = slug, label); storefront tabs and admin dropdowns read it, `CATEGORIES` in types.ts is only a fallback. Why: admins add categories without code changes.
- Product photo arrays are cleaned with `sanitizeImages` before saving, and imports filter photos offline with `looksLikeImage` (no network HEAD checks). Why: per-photo network checks made each import 6–20s slower; `SafeImg` hides any broken photo on the storefront.
- Product import fetches pages directly, then through the Firecrawl reader (normal, then stealth) whenever `looksBlocked` sees a block page or no product signs. Why: shops like Zivame/Myntra block or fake-serve direct requests; no per-site setup.
- Store-wide settings (theme, brand, UPI, feature switches) live in the single-row `store_settings` table, loaded in the root loader; themes are CSS-variable overrides generated by `src/lib/themes.ts`. Why: admin changes restyle the whole site without code.
- Orders are saved by the `placeOrder` server function, which recomputes totals from database prices before UPI opens. Why: customers cannot change prices in the browser.
- Customer chat uses an anonymous session id; customers read their thread only via the `get_chat_thread` function. Why: no customer login needed, and chats stay private.
- Bulk catalog import uses saved `import_channels` (category URL + last scanned page). Manual "Next 10" runs in the browser via `scanChannel`/`importAndSave`; Auto-Pilot is server-side: a per-minute managed schedule hits `/api/public/jobs/autopilot`, which runs `pilotTick` for every channel with `autopilot=true` in parallel inside `waitUntil` — a continuous worker `pool` imports `IMPORT_CONCURRENCY` links at once within the tick budget, scans harvest `PILOT_BATCH` links fetching several listing pages in parallel, and there is no queue delay; the browser loop uses the same pool. Why: high throughput (1000+/hour) while each tick stays bounded and import continues with the browser closed.
- Product photos are stored as external image links, never copied into storage. Why: keeps tens of thousands of products light.
- Competitor names, "buy on X" promo text and ZI manufacturer codes are wiped by `src/lib/brandwipe.ts` on every entry path (link import, auto-queue, manual admin save, reviews via `reviewSchema`). Why: the storefront must never show another shop's name.
- Category scans drop promo/offer/collection URLs in `extractProductLinks` (`isPromoUrl`) before any detail fetch; auto-queue only saves products with a price, verified photos and sizes. Why: no wasted fetches or junk rows.
- `products.discount_percent` is a generated column from `price`/`old_price` (MRP); store-wide discounts run through the admin-only `apply_bulk_discount` database function in one UPDATE. Why: discount never goes stale and bulk changes are instant.
- Storefront Offers and "Popular" ordering come from pure helpers in `src/lib/merch.ts`. Why: merchandising rules stay testable in one place.
- Admin quick sign-in uses a 4-digit PIN: hash+salt in the service-only `admin_pin` row, verified by `pinLogin` (5 wrong tries lock 15 min), which returns a one-time magic-link token the browser exchanges for a normal session. On a fresh store with no admin, `setupPin` creates the admin account. Why: remixed copies get empty storage, so the owner needs a no-email way back in.
- Backend is Lovable Cloud (managed backend) — email/password auth and Google OAuth are enabled, the admin account exists in `user_roles`, and there is no client-side master-PIN bypass anywhere. The sign-in page resolves `pinStatus` before choosing `pinLogin` vs `setupPin` so an existing admin never hits the first-time setup path. Why: the old external backend connection and the temporary 1234 frontend bypass caused "Unauthorized" errors on every admin save; the real backend session fixes all of them.
- Catalog Dump Bot seeds products through admin-only database functions (`seed_categories`, `seed_catalog_category`, `clear_catalog`); the browser calls them in per-category batches (`dumpPlan` in src/lib/dumpbot.ts) for real progress. Seeded rows write both `products.colors` (read by the storefront) and `product_variants`, using the 5 core colours with 4 bundled photos each from public/seed; `colorsMissingPhotos` blocks saving any colour with fewer than 3 photos. Why: instant generation with no external fetches, and the existing storefront keeps working.
- `admin_settings` holds API keys, so it is admin-only (never public read); public UPI stays in `store_settings`. Why: keys must never leak to shoppers.
- Combo/multi-pack detection uses `COMBO_RE`/`isComboText` in src/lib/extract.ts, shared by import category guessing and the admin "Sets & Combos" filter. Why: one rule decides what counts as a set.
- Firecrawl calls go through one limiter in import.server.ts (FIRECRAWL_MAX at once, global pause on 429), and scanPages throws instead of advancing when every page failed to load. Why: rate-limited pages were counted as scanned, skipping 60 pages with 0 imports.
- AI Designer Studio (src/lib/designer*.ts, AiDesignerPanel) is separate from Dump Bot: AI invents designs in batches of 25, the browser makes photos 4 at once via createDesign, photos live in the private ai-designs bucket behind 10-year signed links; sizes/colours come from pure helpers in designer.ts. Why: real unique designs with every size, without hitting AI rate limits.

- Instant Model Catalog Loader calls admin-only `seed_model_catalog(_cat,_n,_photos)` in chunks of 250 (`chunks` in src/lib/modelCatalog.ts); photo links per category come from CDN asset pointers in src/assets/seed, colours/sizes are fixed in the database function. Why: instant, no scraping or network checks.
- Carousels and banners use native CSS scroll-snap with no timers/animation loops, product cards do no layout reads on pointer move, and lists render 24 at a time. Why: continuous loops froze low-end phones.
- Bulk file import (/admin/import) parses CSV/JSON in the browser via pure helpers in `src/lib/fileImport.ts` and skips any row whose `dedupeKey(source_url)` (normalised link, or `sku:<id>` when no link) already exists, re-checking right before insert. Why: no duplicate products from repeated exports.
